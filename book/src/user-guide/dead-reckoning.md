# Dead Reckoning

`strapdown-sim dr` propagates the strapdown mechanization from the first record using the IMU
alone. No GNSS, barometer or magnetometer measurement is applied, and there is no filter: the
output is the free-inertial solution, with all of its drift.

```bash
strapdown-sim syn -o synthetic.csv --duration-s 600 --seed 42
strapdown-sim dr -i synthetic.csv -o results/dr.csv
```

```console
[INFO] - Running dead reckoning simulation on 6000 records
[INFO] - Mechanizing input as NED: mean vertical specific force over the first 10 record(s) is -9.754 m/s^2 against a local gravity of 9.780 m/s^2
[INFO] - Generated 6000 navigation results
[INFO] - Results written to results/dr.csv
```

(Timestamps trimmed from the log lines.) The flags are only the shared ones -- `-i`, `-o`,
`--enu` and the limit flags -- described in [Running Simulations](./simulations.md). `dr`
takes no seed, because nothing in it is random.

## What it computes

The initial state is taken from the first record:

| State | Source in the first record |
|---|---|
| latitude, longitude, altitude | `latitude`, `longitude`, `altitude` |
| north and east velocity | `speed` and `bearing` (a NaN in either gives zero) |
| vertical velocity | zero; the format carries no vertical rate |
| attitude | the quaternion `qw, qx, qy, qz` (not the `roll`/`pitch`/`yaw` columns) |

Every later record contributes one IMU step, with the time step taken from consecutive
timestamps, through the same mechanization the filters use (Groves §5.4-5.5; see
[The Navigation Model](./concepts.md)). The output has **one row per input record**, the first
being the initial state.

Because there is no filter, there is no covariance. In the output CSV the bias columns are zero,
every covariance column is `NaN`, and the six optional bias columns are empty; see
[Output Format](./output-format.md).

Three practical consequences of having no filter:

- **Every record must carry all six inertial channels.** The filters skip a record with a
  missing accelerometer or gyroscope value and coast across the gap; `dr` has no notion of a gap
  and fails on it. Blanking a single `acc_x` cell in a synthetic file stops the run with
  `Error: NonFinite { what: "propagated attitude matrix" }`, where `cl` on the same file logs a
  tolerated 0.2 s gap and finishes.
- **The limit flags are inert.** `dr` accepts `--max-wall-clock-*`, `--health-*` and
  `--nis-pos-*` and applies none of them, so a run that drifts a long way is written out in full
  instead of being cut off.
- **The frame check still runs.** Declaring the wrong frame is the one mistake that would make
  dead reckoning fail at 2 g rather than drift, so it is refused before propagation exactly as in
  the other modes; see [Input Data Format](./data-format.md#frame-convention).

## What it is good for

- **An error-growth baseline.** Dead reckoning is the reference every aided result is measured
  against: the gap between a `dr` run and a `cl` run on the same input is what the aiding bought.
- **Checking an IMU and a dataset.** A wrong frame, a units mistake or a mis-scaled channel shows
  up in the first seconds of a `dr` run, before any filter tuning can hide it.
- **Seeing what a sensor grade means.** On synthetic data the only error source is the IMU model
  `syn --imu-grade` selects, so the same trajectory at different grades shows how quickly each
  grade drifts; see [Synthetic Trajectories](./synthetic.md#imu-grades).

## How much it drifts

The repository's accuracy suite carries one dead-reckoning scenario, `syn_dead_reckoning`: the
first 120 s of a synthetic 50 m/s cruise with a consumer-grade IMU, scored against the
trajectory's exact truth. Its current numbers are the `syn_dead_reckoning` rows of the tables
under [Performance Baselines: Current values](../development/performance.md#current-values),
which are regenerated by `core/tests/perf_baseline.rs` rather than written by hand.

The same input can be produced from the command line. These two commands write the scenario's
sensor records and its truth; dead reckoning the first and scoring it against the second
reproduces that row's vertical RMSE and vertical bias exactly:

```bash
strapdown-sim syn -o cruise.csv --duration-s 120 --sample-rate-hz 50 \
  --latitude-deg 40 --longitude-deg=-75 --altitude-m 200 \
  --velocity-north-mps 40 --velocity-east-mps 30 --yaw-deg 36.86989764584402 \
  --gnss-horizontal-noise-m 3 --gnss-vertical-noise-m 5 --baro-noise-std-pa 30 --seed 42
strapdown-sim syn -o cruise_truth.csv --no-noise --duration-s 120 --sample-rate-hz 50 \
  --latitude-deg 40 --longitude-deg=-75 --altitude-m 200 \
  --velocity-north-mps 40 --velocity-east-mps 30 --yaw-deg 36.86989764584402 \
  --gnss-horizontal-noise-m 3 --gnss-vertical-noise-m 5 --baro-noise-std-pa 30 --seed 42
strapdown-sim dr -i cruise.csv -o cruise_dr.csv
```

The suite deliberately stops at 120 s. Unaided consumer-grade dead reckoning over a long
recording runs away -- its altitude eventually reaches a value at which the transport-rate
denominator $r_e + h$ approaches zero, where whether the numbers stay finite is a floating-point
accident that has differed between platforms. Expect a long `dr` run on MEMS data to diverge,
and read it as a demonstration of why aiding exists rather than as a navigation result.

## `ol` is not dead reckoning

The `ol` subcommand is a separate, **unimplemented** mode. It validates its paths, creates the
output directory, prints `Open-loop mode is not yet fully implemented` and writes nothing. Dead
reckoning is `dr`. In a configuration file the corresponding mode names are `dead-reckoning` and
`open-loop`; the latter exits with an error.
